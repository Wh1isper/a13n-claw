# Project

A Project is a Claw-owned entity that gives one Claw a persistent working context. Its Main and managed worker Threads share that context. Service Workspace is the administrative and authorization scope for the native resources the Project references.

## Working Context

A Project can be saved before execution resources are configured. Its runtime binding selects one concrete Service Environment and, optionally, one concrete Service Browser in the Workspace. An Environment template or Browser provider is a creation input, not a runtime binding. Before the Environment is bound and available for execution, incoming work remains in the Inbox and Claw does not launch Main or an idle heartbeat.

Main and shared-environment workers use the selected working files and tooling. Main may also use the selected Browser; native child Threads do not inherit a Browser automatically. Native fresh-Thread schedules capture both Project bindings in their invocation. Archive enabled or paused fresh-Thread schedules before replacing either binding. Service owns preparation, start, stop, and recovery. A supported stop preserves the resource identity and the state guaranteed by its provider; the binding survives it. Main going idle does not stop resources used by workers. Claw does not replace a deleted or lost instance by starting an empty replacement.

Each new Claw Project creates a persistent native Service Memory Space backed by Service-managed PostgreSQL File Memory. Claw records the Space reference, and Main and its workers use the same authorized Space across Runs and Environment replacement. Service owns memory and its access grants. Shared files, memory, and browser state do not merge the Threads' conversation histories. Any broader memory sharing comes from explicitly authorized Service resource access, not from installing Claw or placing Claws in the same Workspace.

## Execution Identity

Each Workspace uses one dedicated Claw Service Account with the `builder` role: `read`, `run`, and `write`, without `admin`. Claw Control and its Main, native Worker, and fresh scheduled executions use that same account. Service captures its Workspace execution verbs when admitting Runs and Schedules; subsequent grant changes cannot expand an existing capture. Workspace `write` is available to the execution through authorized Service operations, so this account is not a run-only identity. Interactive operator actions retain the operator's own authorization. For an interactive Fresh Schedule request, Claw records the operator as the requester; the native Schedule creation is separately audited under the executing Claw account.

## Agent Composition

Claw automatically supplies useful native capabilities to Main and workers according to the Environment, optional Browser, and other resources actually available to each execution. These include file and command operations, context summary, background execution, and collaboration where supported and authorized. Service's resource grants and execution policy remain authoritative. Operators do not select individual default tools for each Claw.

Claw uses a selected Service Agent and contributes the system instructions needed for its Inbox, communication, delegation, and [scheduled work](02-main-thread.md#scheduled-work). The execution includes those instructions and the automatic capabilities alongside the Agent's configured instructions, MCP, and other toolsets; Claw's contribution does not discard the Agent's configuration. Configure additional MCP and other toolsets on that Agent in Service. An Agent with no operator-authored tools or instructions can work when a usable model and the required resources are available; unavailable resources do not become available merely through composition.

An operator can select named Worker Agents and provide dynamic Worker model choices with descriptions of the work each suits. Claw pins safe revisions of selected Agents and includes model guidance in Main's instructions. Main chooses a suitable model when delegating; descriptions do not impose a fixed router. Service also permits Main's own model for a dynamic Worker, even when it is not in the configured list.

Optional Shell Review selects a Workspace Model, risk threshold, and instruction for reviewing shell execution. It does not grant an operation denied by the source Agent. Flagged calls and review errors are denied rather than suspended for approval.

## Continuity and Ownership

Claw records the Project's resource references and its Thread associations. Service owns preparation, access, and lifecycle of the native resources, and its grants apply to each use. When a required resource is missing, unavailable, or not authorized, surface the affected Project and operation; an empty replacement cannot stand in for the original working state. Recovery or replacement is an explicit operator action. A shared native child captures the parent Run's mounts at admission. Replacing the Project Environment requires Main and the affected shared lineage to have no active or resumable waiting Run and no pending native Inbox entry; otherwise the operator must finish that work and retry. Service updates descendants reached through dynamic or named shared edges, including descendants whose primary Environment was independently rebound. Dedicated and none-policy branches are not traversed. Native child Browser bindings are independent and are not rebound with Main. An accepted Run retains its captured resources and native continuation semantics. Updating an existing desired Thread binding requires Service's version and idleness checks; it is not a hot rebind. Rebinding moves neither working files nor browser profiles. Service-owned schedule definitions and accepted occurrences keep their saved execution selections; the operator retires incompatible definitions before rebinding. The ownership boundary also applies to [backup and restore](05-operator-workflows.md#backup-and-restore): restoring a Project reference does not restore the data behind it.
